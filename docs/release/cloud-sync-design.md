# Local observation sync — implementation proposal

**Status: proposal only, 14 September 2026.** Reviewed source: `bbe0a4e1b5b5adae64377e7cae79a93d5e808074`. No sender, outbox, pairing bridge or cloud lifecycle changes are implemented by this document. This is the narrow FR002/008/011/013/015/016/020/067 design for the existing laptop and online management console. It introduces no cloud inference, footage upload, person identification, remote alarm or new hardware. The current standalone cloud companion is a connection-heartbeat utility, not an observation synchroniser.

## Smallest useful product

A local pharmacy manager explicitly pairs one existing pilot installation and one local branch with one server-authorised cloud laptop/pharmacy. New eligible observations committed after pairing appear in the cloud review feed, with a stable receipt and visible local delivery status. A restart or lost response cannot create a duplicate. Local detection and sound remain under their existing attended-browser controls.

The first version sends **historical management observations**, not real-time remote alarms. Every outbound observation has `historical: true`, including an immediately delivered live-source observation. This conservative choice preserves a byte-stable retry payload and avoids implying that upload arrival proves current monitoring. The cloud cannot sound the laptop, start detection or create a case automatically. A cloud case still requires an authenticated human review in the existing console.

Only these content fields leave the laptop: generated event UUID, allowlisted event code, a fixed generic source/camera-position label, local server admission timestamp and the historical flag. Device registration already has its explicitly entered laptop name/platform. Do not send source window/tab/file titles, URLs, camera credentials, staff names, actor/session identifiers, track/person IDs, model narrative, review notes, case notes, product/patient details, JPEGs, audio, media hashes, evidence paths or media links. Operational identifiers and timestamps are minimised metadata, not a claim of anonymity.

Default eligible class: completed `POSSIBLE_CONCEALMENT` with the existing server-derived `alarm_eligible == true`. Pose-rule observations are a separately labelled, default-off manager option. Ordinary pickup/return classes have protocol mappings below but stay off in the first release to avoid filling the attention queue with normal shopping. Failed/cancelled/unclear jobs never become suspicious-activity alerts. Recordings and synthetic-mode databases are excluded from live cloud sync, without a toggle that mixes test events into a real pharmacy feed.

## Pairing and staff flow

1. In the online console, an authorised owner/manager creates the laptop enrolment for the intended pharmacy. On the local **Cloud connection** page, a local `MANAGER` sees the active local branch, the exact HTTPS destination, the pairing purpose and the fields to be shared. No token goes in a URL, command argument, log or browser storage.
2. Enrollment/reuse of an already enrolled credential happens on the local server, using the platform's verified private credential adapter. Before consuming a one-use code, verify that the credential destination is safe and writable. Do not import or run the standalone companion simultaneously with an integrated sender using the same credential/sequence.
3. Add `GET /device-api/identity` with device bearer authentication, returning only `{device_id, organisation_id, organisation_name, pharmacy_id, pharmacy_name, name, platform, app_version}` from the authenticated device's server join. No directory, staff details, token or other-device information is returned. The route must enforce active pharmacy and nonrevoked device in the same lock order as existing device intake. It need not migrate the database. Existing strict enrolment-response clients remain compatible because the enrolment response is unchanged.
4. Local server stages a short-lived pairing candidate after this call. Staff confirm **local branch ID/name → cloud pharmacy ID/name + laptop + exact origin**. Names are display information, never the mapping rule. Commit only after fresh local manager/branch authority, candidate expiry, candidate revision and unchanged server identity are checked. Network requests must occur outside the local authentication/SQLite transaction; revalidate authority after I/O. A manager of one local branch cannot bind another via a supplied ID.
5. Persist a new immutable binding generation and enable the selected event policy. No backfill of existing history. A pending model job submitted before pairing, or under an earlier binding generation, is not silently picked up when it later completes. Confirm a fresh local source/run separately; pairing never arms sound.
6. Show connected target, last successful heartbeat, monitoring **Unknown**, sharing enabled/paused, pending count, oldest pending age, last receipt time, expired/skipped counts and a bounded error category. “Queued”, “received by management”, “expired before upload” and “withdrawal pending” are distinct. Offline management never says local detection stopped solely because sync failed.

Use one active device binding per pilot installation for the first version. A cloud device is fixed to one cloud pharmacy. A local branch switch never redirects its queue: the new branch shows “This branch is not paired”; previously committed rows retain the old immutable binding and may drain only while that binding remains enabled. Moving the laptop to a different branch requires explicit disconnect and a fresh device pairing. Old rows must not be rewritten to the new token/device/branch.

An enrolment response lost after server commit cannot be recovered from the current one-use API. Preserve any credential successfully stored, stop, and show that the owner must revoke the orphan device in the console before creating another code. Do not automatically loop enrolment. A lost local confirmation response is handled by a local idempotency key and candidate revision.

## Durable local state and transaction hooks

Use additive tables in the **same pilot SQLite database**, not a second spool database. One schema owner must update the version/provenance checks and backup compatibility. Existing older binaries currently accept schema versions 0/1/2; a new version must make unsupported rollback fail before writes. Do not edit previously deployed cloud migrations.

Proposed records:

- `cloud_bindings`: binding UUID/revision, local organisation/site IDs, exact cloud origin, server-verified cloud organisation/pharmacy/device IDs, installation UUID, nonsecret credential handle, policy version/allowlist, state and bounded operational timestamps/errors. Credentials remain outside SQLite in the verified platform store. One active binding per installation; no mutable target fields.
- `cloud_outbox`: outbox UUID, binding UUID, local entity kind/ID, stable cloud source UUID, operation (`OBSERVATION` or later `WITHDRAWAL`), immutable canonical payload and its SHA-256, state, attempt count, retry time, lease owner/expiry, creation/deadline, receipt ID/time. Unique `(binding_id, local_kind, local_id, operation)`. Payload maximum 2 KiB. Every access checks local scope as well as the binding ID.
- `cloud_sync_state`: per-binding monotonic heartbeat sequence, last accepted heartbeat, worker ownership/lease, bounded counters and one current error code. A process generation makes expired work leases reclaimable; no browser tab owns the sender.

Store only the allowlisted payload, not a copied entity JSON. A dedicated authenticated-encryption envelope for outbox payloads uses a separate platform-protected sync key and AAD binding installation, local scope, binding, outbox UUID and schema version. Do not reuse the JPEG cipher format/nonce domain. If this key is unavailable, stop sync and show it; never fall back to plaintext or replace an existing key. Nonsecret routing/status columns remain in the existing private database. This protects the spool within the existing laptop account limits, not a compromised logged-in machine.

Do not call an HTTPS endpoint inside `Store.transaction()` or the `context()` dependency, which holds a write transaction for its entire scope. Sender claims a due row in a short transaction, closes it, sends bounded HTTP, then commits a receipt only if its binding/lease still matches. On crash after claim or after cloud commit, replay the **same payload/UUID**. No polling/backfill of `entities` after restart: it would resurrect deliberately excluded/deleted observations and miss older rows hidden by listing limits.

Restored backups start **disconnected**, preserving existing outbox identities for inspection. Credential keys are not exported in ordinary support archives. Do not clone a device token or resume a copied installation's heartbeat sequence automatically. A restored original can resume only through a deliberate identity/sequence reconciliation procedure; otherwise revoke/re-pair and discard the old queue with a visible count. Never re-key old observations to evade cloud deduplication. Backup/restore changes belong to the schema owner's phase.

## Payload mapping accepted today

Existing request shape, with no extra fields:

```json
{
  "source_event_id": "00000000-0000-5000-8000-000000000001",
  "event_code": "POSSIBLE_CONCEALMENT",
  "source_label": "Camera 2 of 6 · 3x2 screen grid · local observation",
  "occurred_at": "2026-09-14T12:00:00Z",
  "historical": true
}
```

The example uses a synthetic canonical UUID. Generate a UUIDv5 using a fixed application namespace plus installation UUID, immutable binding UUID, local scope, entity kind and local stored ID; persist the result. The cloud's device ID is an additional server-side deduplication scope. Never recompute an identity from time, current layout, retry count or the selected UI branch.

| Local input | Cloud mapping / first-version policy |
| --- | --- |
| `result.action == POSSIBLE_CONCEALMENT` and server `alarm_eligible == true` | `POSSIBLE_CONCEALMENT`, default eligible. This is an experimental model observation requiring review. |
| `TAKE_PRODUCT` / `RETURN_PRODUCT` | `POSSIBLE_PRODUCT_TAKE` / `POSSIBLE_PRODUCT_RETURN`; default excluded, no inference that pickup/return is suspicious. |
| `REPEATED_HAND_TO_WAIST` / `RESTRICTED_ZONE_ENTRY` | Same code; separately enabled pose-pattern metadata only. No track ID, sound status or wrongdoing assertion. |
| `NORMAL_SHOPPING`, `UNCLEAR`, `PLACE_IN_BASKET`, failed/cancelled jobs | No cloud alert. |
| Runtime `monitoring_allowed`, model health or browser stopped event | No synthetic activity alert and no `ACTIVE` heartbeat. `CAMERA_UNAVAILABLE`/`MODEL_UNAVAILABLE` are accepted by cloud but lack a durable, camera-bound transition source locally; leave them out until separately designed. |
| Any `RECORDED_VIDEO`; synthetic database | Excluded. A synthetic test console may exercise fixtures in isolated tests, never a real pharmacy binding. |

Generate `source_label` from constants and validated numeric context only: `Camera N of M · 2x2/3x2/2x3 screen grid · local observation`, `Camera source · local observation`, or `Screen area · local observation`. Do not reuse `item.source_label` or append a filename/window title. The camera number is a screen position, not a physical camera identity. Store full validated `camera_context` only locally with the immutable observation/outbox lookup; a layout/epoch/source change cannot change an existing payload. The current cloud feed cannot show exact crop geometry or distinguish repeat visits to the same physical camera, and must not claim that capability.

For both kinds use the persisted **local API admission time** (`created_at`) as the bounded management observation timestamp. Product frames have media-relative seconds, not a trustworthy UTC capture timestamp; live `detected_at` is browser-declared. Do not reconstruct capture UTC from recording offsets. The cloud UI must label this field “Reported observation time — laptop clock” for synced observations, not verified capture time. Until a future explicit timestamp-basis field exists, the generic label and feed help must explain this conservative meaning. Freeze the timestamp once. If it is invalid or outside the cloud window, quarantine/drop with `CLOCK_INVALID`; do not replace it with “now” to get accepted. Cloud receipt time remains independent.

## Delivery, bounds and connection health

One network operation at a time per installation, with round-robin priority between an overdue heartbeat and the oldest due eligible observation; withdrawal obligations take priority over ordinary uploads. Never build a memory queue from all stored rows. Preserve the existing HTTPS exact-origin validation, no redirects, no inherited proxies, TLS verification, eight-second timeout and 64-KiB response bound. Parse only allowlisted error codes; never store response bodies or exception text containing secrets. Alert receipt must have canonical UUID `id` and `received == true`; malformed success is an uncertain delivery and retries the same payload.

Persist heartbeat sequence reservation and body before sending. On restart use a strictly higher sequence for a newly generated connection report; an exact retry uses the previous immutable body. An identical accepted retry does not refresh cloud `last_seen_at`, so the next scheduled heartbeat must use a new sequence. Report `monitoring_status: UNKNOWN`, `camera_count: 0`, a fixed build version and no queue-derived camera count. Send every 30 seconds while the integrated application is running. A successful upload is not proof of monitoring or speaker readiness. Cloud already projects offline/revoked devices to `UNKNOWN` after the 120-second connection window.

Proposed initial limits: 500 outstanding observations and 1 MiB encrypted payload bytes per binding; 1,000 rows/2 MiB per installation; at most 500 new outbound observations per binding per rolling day; at most one alert start per second. Explicitly count and display records skipped by these limits. Do not evict undelivered high-priority rows to pretend delivery succeeded. Maintain a separately bounded withdrawal lane and stop new exports when its obligations cannot fit. Retain only receipt IDs/hash/status after acknowledgement; remove payload bytes immediately after receipt or terminal expiry. Cap receipt/tombstone metadata and prune by a declared replay/retention horizon.

Observation delivery deadline: the earlier of local source expiry and 24 hours after admission; live-event sync gets a 24-hour deadline even though existing live-event storage has no matching janitor. Do not reset this deadline after restart or pairing. Retry transient network/5xx failures with jittered exponential delays (5, 10, 20…300 seconds); persist attempts/next due time, use monotonic time in-process and bounded recalculation after clock changes. On `429`, honour a bounded valid `Retry-After`; `ALERT_LIMIT` gets a long cooldown rather than one-second retries. Never sleep while holding a DB lock.

`401/403` transitions binding to `REVOKED_OR_UNAUTHORISED`, stops sends/heartbeats and requires staff action. The server deliberately does not disclose whether the device, pharmacy or access was revoked. `409 EVENT_CONFLICT` quarantines that row; do not change its UUID/payload. `409 OLD_HEARTBEAT/HEARTBEAT_CONFLICT` pauses device sending and exposes possible duplicate sender/restored state. `422` is terminal validation/time failure. A redirect, wrong origin, TLS failure or oversized/invalid response is never worked around by sending credentials elsewhere. Network failure must not block local inference, review or sound.

## Deletion, retention, disconnect and unresolved completion gate

Before first-attempt delivery, re-read the binding and local source in one short transaction. A deleted/expired source cancels export. There remains an unavoidable race if deletion or disconnect happens after request transmission: the cloud may have committed even if the client cancels or receives no response. Local generation checks prevent recording a misleading new receipt, but cannot undo a remote commit. **A withdrawal protocol is required to close this race.**

Recommended smallest cloud lifecycle addition, owned and reviewed separately from the local SQLite migration:

- Idempotent device-scoped withdrawal by `source_event_id`, accepting only a bounded reason enum (`LOCAL_DELETED`, `LOCAL_EXPIRED`, `LOCAL_EXPORT_REMOVED`). A delete-before-arrival creates a tombstone so an in-flight/late ingestion cannot resurrect it. Repeat withdrawal returns the same safe receipt. No review note or evidence deletion is delegated to a device.
- Server-enforced source expiry for synced observations, bounded to the local 24-hour lifecycle, plus read-time filtering so free-tier sleep cannot expose expired content. This needs a distinguishable sync protocol/version or a dedicated sync route; do not silently apply new lifecycle defaults to unrelated existing device clients. No geometry/media columns are necessary.
- An unlinked expired/withdrawn cloud observation is removed from active feed/counts and its metadata is purged. Keep a minimal `(device_id, source_event_id, payload_hash, withdrawal/expiry state)` tombstone for a defined replay horizon at least as long as the cloud's 30-day accepted event window. Bounded maintenance plus admission caps must prevent indefinite tombstone growth.
- A cloud incident already created by staff has its own reviewed-record lifecycle. Withdrawal must mark its source unavailable and remove exported source details, while preserving the separately authored case and audit according to its policy. Do not silently delete staff notes or claim a local delete erased a cloud case. The current foreign key/DTO assumes an intact alert, so the cloud migration and UI need an explicit unavailable-source representation. That policy and retention horizon are not implemented today.

Until this addition is implemented and tested, only an explicitly described **limited metadata feed** can ship; it is not full end-to-end sync or erasure. A source label and `historical:true` cannot solve remote deletion/retention. Do not auto-enable exports merely because the basic ingestion test passes.

Local controls must distinguish **Pause sharing** (stop new exports and hold valid backlog, while connection-only heartbeats and withdrawals continue), **Resume sharing** (same binding, still-valid rows only), **Disconnect this laptop** (disable binding first, stop new network attempts, discard unsent observations, do not repoint old rows), and **Remove previously shared observations** (withdrawal workflow, where available). Separate sharing-paused state from credential/binding-disabled state. Disconnect is not cloud revocation or deletion. The owner can revoke the device in the online console; a disconnected dashboard ages offline within two minutes. A revoked device cannot submit withdrawals, so unresolved cloud deletion must go through an authenticated cloud-manager action and be shown as unresolved locally. Remove credentials only after the chosen operation's obligations are resolved or explicitly handed over; never silently lose an uncertain-delivery ledger.

An unexpected shutdown leaves receipts/leases recoverable and immediately invalidates any in-memory assumptions. It does not restart detection or sound. Logout/session expiry stops browser detection through existing controls; queued observations were authorised at their original commit and may drain under the explicit manager-owned binding policy without borrowing a staff session cookie. Disabling the binding is the durable way to stop that background delivery.
